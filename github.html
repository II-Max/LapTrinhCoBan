🐙 GitHub – Hợp Tác & Lưu Trữ Đám Mây

Từ push code lên remote đến Pull Request chuyên nghiệp.

1 Tạo Repository & Kết Nối Remote

Cơ bản

Để lưu trữ mã nguồn trên đám mây và cộng tác với đồng đội, bạn cần tạo một repository (repo) trên GitHub rồi kết nối nó với dự án Git trên máy tính của mình.

Tạo Repository trên GitHub

Truy cập github.com → đăng nhập → nhấn nút "New" (hoặc dấu + góc trên bên phải) → đặt tên repo → chọn Public hoặc Private → nhấn "Create repository". GitHub sẽ hiển thị ngay các lệnh để bạn kết nối repo local với repo remote vừa tạo.

Kết nối và đẩy code lên GitHub

Sau khi tạo repo trên GitHub, bạn cần liên kết repo local với remote bằng các lệnh sau:

Bash 
# Thêm remote origin trỏ tới repo GitHub
git remote add origin https://github.com/username/my-project.git

# Đổi tên nhánh mặc định thành main
git branch -M main

# Đẩy code lên GitHub lần đầu tiên
git push -u origin main

Sau lần push đầu tiên với cờ -u (viết tắt của --set-upstream), Git sẽ ghi nhớ nhánh upstream. Những lần sau bạn chỉ cần gõ git push là đủ.

Clone – Tải repo có sẵn về máy

Nếu đồng đội đã tạo repo trước, bạn dùng git clone để tải toàn bộ mã nguồn và lịch sử commit về máy:

Bash 
# Tải repo từ GitHub về thư mục hiện tại
git clone https://github.com/username/my-project.git

# Clone vào thư mục có tên tùy chỉnh
git clone https://github.com/username/my-project.git ten-thu-muc

Lệnh git clone tự động thiết lập remote origin cho bạn, nên bạn không cần chạy git remote add nữa.

💡
SSH vs HTTPS: GitHub hỗ trợ hai giao thức kết nối. HTTPS dễ thiết lập hơn – bạn dùng URL dạng https://github.com/... và nhập mật khẩu (hoặc Personal Access Token). SSH an toàn và tiện lợi hơn vì không cần nhập mật khẩu mỗi lần push – bạn tạo cặp khóa SSH rồi thêm public key vào tài khoản GitHub. URL SSH có dạng git@github.com:username/repo.git. Nếu bạn làm việc chuyên nghiệp, nên dùng SSH.

2 Git Pull & Đồng Bộ Với Đồng Đội

Cơ bản

Khi làm việc nhóm, code trên GitHub luôn thay đổi vì đồng đội liên tục push commit mới. Bạn cần đồng bộ (sync) repo local với remote để luôn có phiên bản mới nhất.

git pull – Kéo và gộp tự động

Lệnh git pull thực chất là tổ hợp của hai lệnh: git fetch (tải dữ liệu mới từ remote) và git merge (gộp dữ liệu đó vào nhánh hiện tại). Đây là cách nhanh nhất để cập nhật code:

Bash 
# Kéo và gộp code mới nhất từ remote
git pull origin main

# Hoặc tách riêng: tải về trước, gộp sau
git fetch origin
git merge origin/main

Khi nào dùng pull, khi nào dùng fetch + merge?

Tình huống Nên dùng Lý do
Cập nhật nhanh đầu ngày làm việc git pull Nhanh gọn, một lệnh duy nhất
Muốn xem trước thay đổi trước khi gộp git fetch + xem diff + git merge An toàn hơn, tránh gộp nhầm code lỗi
Đang có thay đổi chưa commit git fetch rồi xử lý sau Tránh conflict bất ngờ khi merge tự động

Sau khi git fetch, bạn có thể dùng git log origin/main hoặc git diff origin/main để xem trước những gì đồng đội đã thay đổi, sau đó mới quyết định merge.

⚠️
Luôn pull trước khi push: Nếu bạn push mà chưa pull code mới nhất, Git sẽ từ chối (rejected) vì lịch sử commit không khớp. Hãy tạo thói quen chạy git pull trước mỗi lần push để tránh xung đột không cần thiết.

3 Pull Request (PR) – Quy Trình Chuẩn Công Ty

Quan trọng

Pull Request (PR) là cơ chế cốt lõi của quy trình cộng tác trên GitHub. Thay vì push thẳng vào nhánh main, bạn tạo nhánh riêng, hoàn thành tính năng, rồi mở PR để đồng đội review code trước khi merge. Đây là tiêu chuẩn tại mọi công ty phần mềm chuyên nghiệp.

Quy trình Pull Request từng bước

  1. Tạo nhánh mới cho tính năng hoặc bản sửa lỗi: git checkout -b feature/ten-tinh-nang
  2. Code, test, commit – hoàn thành tính năng trên nhánh riêng của bạn, viết commit message rõ ràng
  3. Push nhánh lên GitHub: git push origin feature/ten-tinh-nang
  4. Vào GitHub → New Pull Request – chọn nhánh nguồn (feature) và nhánh đích (main), viết mô tả PR
  5. Đồng đội Review → Approve → Merge – đồng đội đọc code, góp ý, approve rồi merge vào main
Bash 
# Bước 1: Tạo nhánh mới cho tính năng
git checkout -b feature/login-page

# Bước 2: Code xong → commit
git add .
git commit -m "feat: thêm trang đăng nhập"

# Bước 3: Push nhánh lên GitHub
git push origin feature/login-page

# Bước 4-5: Vào GitHub → New Pull Request → Review → Merge

Tại sao Code Review quan trọng?

Code review thông qua PR mang lại nhiều lợi ích:

  • Phát hiện bug sớm – đồng đội có thể thấy lỗi logic mà bạn bỏ sót
  • Chia sẻ kiến thức – cả team hiểu codebase, không ai là "người duy nhất biết"
  • Nâng chất lượng code – góp ý cải thiện cách đặt tên biến, cấu trúc, hiệu suất
  • Lịch sử rõ ràng – mỗi PR ghi lại lý do thay đổi, dễ tra cứu sau này
  • Bảo vệ nhánh main – tránh code lỗi vào production
💡
Viết mô tả PR tốt: Một PR chuyên nghiệp nên có: tiêu đề ngắn gọn mô tả thay đổi, phần "Mô tả" giải thích tại sao cần thay đổi này, danh sách những gì đã thay đổi, ảnh chụp màn hình (nếu liên quan đến UI), và link tới issue/task tương ứng. PR tốt giúp reviewer hiểu nhanh và approve sớm hơn.

4 Xử Lý Merge Conflict

Nâng cao

Merge conflict xảy ra khi hai người cùng sửa cùng một dòng trong cùng một file, và Git không biết nên giữ phiên bản nào. Đây là tình huống rất phổ biến khi làm việc nhóm – đừng hoảng sợ, hãy bình tĩnh xử lý!

Nguyên nhân gây conflict

  • Hai người cùng sửa một dòng code trong cùng một file
  • Một người xóa file mà người khác đang sửa
  • Hai nhánh cùng thêm code vào cùng vị trí trong file
  • Không pull code mới trước khi bắt đầu làm việc

Nhận diện conflict markers

Khi conflict xảy ra, Git sẽ đánh dấu vùng xung đột trong file bằng các ký hiệu đặc biệt:

Text 
<<<<<<< HEAD
code của bạn (nhánh hiện tại)
=======
code của đồng đội (nhánh đang merge vào)
>>>>>>> feature/other

Phần trên dấu ======= là code của bạn (HEAD – nhánh hiện tại). Phần dưới là code từ nhánh đang được merge vào. Bạn cần quyết định giữ phần nào, hoặc kết hợp cả hai.

Các bước xử lý conflict

  1. Mở file bị conflict – Git sẽ liệt kê các file conflict sau lệnh merge/pull
  2. Chỉnh sửa file – giữ code đúng, xóa bỏ hoàn toàn các dòng marker (<<<<<<<, =======, >>>>>>>)
  3. Stage file đã sửa: git add .
  4. Commit để hoàn tất merge: git commit (Git tự tạo message "Merge...")
Bash 
# Sau khi sửa xong file conflict
git add .
git commit -m "resolve conflict: hợp nhất trang đăng nhập"

# Hoặc để Git tự tạo commit message mặc định
git add .
git commit

Xử lý conflict bằng VS Code

VS Code cung cấp giao diện trực quan cực kỳ tiện lợi để xử lý conflict. Khi mở file có conflict, VS Code hiển thị:

  • Accept Current Change – giữ code của bạn (HEAD)
  • Accept Incoming Change – lấy code từ nhánh đang merge
  • Accept Both Changes – giữ cả hai phần code
  • Compare Changes – xem so sánh song song hai phiên bản

Bạn chỉ cần click vào lựa chọn phù hợp, VS Code sẽ tự động xóa các conflict markers và sắp xếp code cho bạn.

🚨
Đừng bao giờ chấp nhận mù quáng một phía: Khi gặp conflict, nhiều người có thói quen luôn chọn "Accept Current" hoặc "Accept Incoming" mà không đọc kỹ code. Điều này cực kỳ nguy hiểm vì có thể xóa mất tính năng của đồng đội hoặc ghi đè lên bug fix quan trọng. Luôn đọc hiểu cả hai phần code rồi mới quyết định giữ phần nào, hoặc kết hợp cả hai thành phiên bản hoàn chỉnh nhất.
